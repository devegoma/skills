# TDD From Plan

`docs/work-plan.md` の作業計画に従って対象項目を実装し、検証後にチェック状態を更新する。計画の範囲と制約を守り、コード変更はテスト駆動で小さく進める。

## 手順

1. `docs/work-plan.md` を読み、引数で指定されたセクションまたはチェック項目を特定する。計画書がない場合は作成・実装せず、その旨を報告する。
2. 引数の指定がなければ、文書末尾側にある最新の未完了作業セクションから未完了項目を選ぶ。過去の作業結果や完了済みセクションに残った未チェック項目は対象にしない。該当項目がない場合、または対象を一意に選べない場合は実装せず、確認または状況報告で止める。
3. 対象セクションの目的、範囲、制約、完了条件、依存関係、未完了項目を確認する。リポジトリの規約と既存変更を調べ、変更範囲とリスクを把握する。前提が未確定で判断により仕様や範囲が変わる場合は、該当項目に着手する前にユーザーへ確認する。
4. コード変更に着手する前に `ponytail` スキルを読み、必要な変更を絞って最小の完全な実装にする方針を適用する。続けて `tdd` スキルを読み、その手順を適用する。テストを書く前に、対象の公開インターフェースとテストする seam を明示してユーザーの合意を得る。合意が未取得ならテストを作成せず、確認する。
5. チェック項目を計画の順に一つずつ進める。コード変更では、合意済みの seam に対する失敗するテストを先に追加または更新し、そのテストを実行して失敗を確認する。次に、テストを通す最小限の実装を行い、同じテストを再実行する。既存のテスト様式を優先する。
6. 調査、合意、環境確認、文書更新などコード変更を伴わない項目にはテストを無理に作らず、計画に記載された確認方法で検証する。
7. 対象項目に必要な実装とすべてのテスト・検証が成功した時点で、計画書の該当項目を直ちに `[x]` に更新する。実装だけ完了した場合、検証が未実施または失敗の場合、依存作業や承認が不足している場合は `[ ]` のままにし、理由と必要な対応を記録する。
8. 検証に失敗したら原因を調べ、対象範囲内で修正して同じ検証を再実行する。対象範囲外の変更や無関係な既存エラーの修正は行わない。計画変更が必要になった場合は、理由を計画書に記録してユーザーの確認を得る。
9. 過去の計画記録を削除・書き換えず、対象セクションに実施した検証と結果、未完了項目、残課題を事実に基づいて追記する。計画にないデプロイや破壊的操作は行わない。
10. 最後に、完了した項目、実行した検証と結果、未完了項目、ブロッカーを簡潔に報告する。

## 判断基準

- 計画に複数の対象候補がある、完了状態が曖昧、または依存関係を判断できない場合は、推測で選ばずユーザーに確認する。
- テストは計画とユーザー合意にある公開境界で行い、未合意の内部実装や private method をテスト対象にしない。
- 各 TDD サイクルは一つのテストと最小限の実装に絞る。将来の項目を先取りせず、テストと実装をまとめて一括作成しない。
- 検証結果を得ていない項目は完了扱いにしない。失敗した検証も成功として記録しない。

## 完了条件

- 対象項目を計画の範囲・順序・制約に沿って処理した。
- コード変更の各単位で、合意済みの seam に対する失敗テストを先に確認し、最小限の実装後に同じテストを成功させた。
- 非コード項目は計画に定めた確認方法で検証した。
- 計画書のチェック状態、検証結果、未完了項目、残課題が実際に確認できた事実と一致している。
- 対象外の変更、計画にないデプロイ、破壊的操作を行っていない。
